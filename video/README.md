### 화면에 올린 수치의 출처

1부 영상의 모든 수치는 이 저장소의 `outputs/tables/*.csv` 에서 읽어 온 것입니다.
값을 손으로 옮겨 적은 경로는 없고, 대본이 하려는 **주장마다 검사식(불변량)** 을 걸어
하나라도 거짓이면 제작이 중단되도록 했습니다. 최종 **40/40 통과**.

화면의 색 규칙도 여기서 나옵니다.

- **회색 점선** — 연구자가 정한 기준값 (예: 종합점수 가중치, 목표 피복률)
- **강조색** — 데이터에서 계산된 값

둘을 섞어 말하지 않기 위한 구분이며, 4편 마지막 구간이 이 규칙 자체를 설명합니다.
2부·3부도 같은 색 규칙을 씁니다.

### 화면의 수치는 어디서 왔나

- 출처는 **포드 FULL 실행본**입니다. `자원최적화_실험전용` 노트북을 KAMP 포드(Tesla V100)에서 FAST 모드 False로 끝까지 실행한 결과입니다.
- 노트북 셀 출력(HTML 표와 출력 텍스트)을 파싱해 한 파일에 모았고, 씬 코드는 그 파일에서만 값을 읽습니다. 손으로 옮겨 적은 숫자는 없습니다.
- 지표는 직접 다시 구현해 재계산했습니다. 검사식(불변량) **1146/1146 통과** — 블록 부트스트랩의 신뢰구간·p값, 선정 스코어카드, 순위상관까지 포드 값과 같게 재현됩니다.
- 대본의 비교 주장("A가 B보다 낫다", "1위다")도 검사식으로 걸었고, 대본의 모든 숫자는 계산값과 자릿수까지 대조했습니다.

**1부와 수치가 다른 곳.** 1부는 로컬(Windows) 실행 CSV를, 2부는 포드 실행본을 씁니다. 두 실행은 대부분 같지만
**DNN 수치**(테스트 MAE: 포드 10.331), 추론시간, 스코어카드 점수, 오경보가 몰린 시간대가 다릅니다.
스코어카드 점수가 다른 이유는 학습시간이 아니라, DNN 값이 min-max 정규화의 양끝을 옮기기 때문입니다.
재계산으로 확인했고, 모델 05편에서 설명합니다.

### 영상에서 짚은 '읽을 때 주의할 점'

- Peak-MAE 는 테스트에서 **2시간**으로만 계산됩니다(마스크가 y_avg ≥ θ, θ 는 peak15 기준) — 평가지표 04
- Peak-MAE 구현(y_avg 마스크)은 설계 문서 PRD 2.7절의 정의(y_peak ≥ θ)와 다릅니다 — 평가지표 04
- 보정 후 ECE 0.000 은 같은 OOF 로 맞추고 잰 **인샘플** 값입니다 — 평가지표 08
- 노트북의 "Recall CI 폭 0.37"은 모델 결과가 아니라 clopper_pearson(10, 28) **예시 계산**입니다 — 평가지표 11
- D1/D2 순위상관의 p 0.0048 은 t 근사로 구한 값이고, 모델 6개의 정확한 순열 p 는 12/720 = 0.0167 입니다 — 평가지표 11
- 최종모델(2단계 레짐)은 하이퍼파라미터 튜닝을 받지 않았고, 폴드 3 에서는 단일 LightGBM 에 집니다 — 모델 07
- 테스트 MAE 13.56% 개선은 통계적으로 유의하지 않습니다(p=0.067) — 평가지표 10
- 블록 부트스트랩의 관측 차이 0.819 중 57.6% 가 9월 4일 하루에서 나옵니다 — 평가지표 10
- 피크 저감의 전력량요금 차액은 대리 계산값입니다 — 평가지표 13
- Optuna 탐색에서 고정한 `bagging_freq=1` 이 `best_params` 에 담기지 않습니다. 그래서 최종 LightGBM·피크 직접분류기에는
  이 값이 전달되지 않고, 탐색으로 찾은 `bagging_fraction` 도 실제 학습에서 쓰이지 않습니다(s05:227·245·254, s05:453·474-475) — 모델 06·08
- 분위회귀 세 모델을 따로 학습해서, 테스트 첫 7일 중 19.0% 의 시간에서 분위 순서가 뒤집힙니다 — 모델 09
- sMAPE 의 '분모 0 제외' 장치는 이 데이터에서 한 번도 작동하지 않았습니다(평균전력 0 은 계측정지로 보고 보간했기 때문) — 평가지표 03
- 문서의 "FP 82→45"는 Recall 이 다른 두 지점을 비교한 값입니다. 같은 Recall 1.0 끼리 비교하면 피크 직접분류가 FP 48 로 가장 적습니다 — 모델 02, 평가지표 06

### 만든 방법

ManimCE 0.20.1 과 raenim 으로 화면을 그리고, edge-tts(ko-KR-HyunsuMultilingualNeural)로 나레이션을 합성했습니다.
대본과 애니메이션을 샷 목록 하나에서 함께 만들어서, 대본을 읽는 시간과 영상 길이가 맞습니다.
편마다 다음 검수를 거쳤습니다.

- 정적 린트
- 480p 스모크 렌더의 샷별 프레임 전수 검수(결함을 고친 뒤 다시 확인)
- 1080p 본번 렌더의 표본 검수
- 길이·해상도·자막 트랙 검증

생성 이미지는 쓰지 않았습니다(0컷).

### 화면의 수치는 어디서 왔나 (3부)

- 1·2부와 달리 **이 저장소의 FULL 실행 번들**(`outputs/models/full/eval`·`deploy`)을 번들 매니페스트와 같은 라이브러리 버전
  (lightgbm 4.7.0 · numpy 2.3.5 · pandas 3.0.5)으로 직접 돌려 잰 값입니다. 저장소 파일은 읽기만 했고, 변조 실험은 번들 **복사본**으로 했습니다.
- 대본의 주장은 검사식(불변량) 55개로 걸었습니다 — 예: 9/1~9/14 리플레이 336행이 제출 파일과 전부 일치(MAE 5.2199),
  `bundle_id` 끝 12자리 = 매니페스트 지문, 배포 번들의 τ 출처 = 평가 번들, 서빙 테스트 181개 수집·단위+코드생성 123개 통과.
- 지연시간·로드 시간(예: API 응답 중앙값 약 100 ms)은 제작 PC 에서 잰 값이라 다른 컴퓨터에서는 달라집니다.
- 화면 코드의 `"..."` 는 한글 메시지 문자열, `"<rain>"` 같은 꺾쇠는 한글 컬럼명을 API 영어 별칭으로 줄여 쓴 것입니다(고정폭 글꼴에 한글이 없어서).
